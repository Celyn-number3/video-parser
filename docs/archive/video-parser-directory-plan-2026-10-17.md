## 2. 建议目标布局

以下是**迁移完成后的候选布局**，不是当前目录，也不表示已经获准执行。只在确有内容时创建目录。

```text
video-parser/
├─ src/video_parser/        后端源码；保持既有包与分层
├─ frontend/
│  ├─ src/                 前端源码
│  ├─ prototypes/          经核对后归入的 UI 原型
│  ├─ dist/                生产构建产物，不当源码维护
│  └─ node_modules/        本机依赖，不搬迁或纳入 Git
├─ tests/                  offline / browser / live / fixtures
├─ scripts/                启动实现、安装、诊断和维护
├─ configs/                业务配置
├─ requirements/           分运行条件的工具依赖
├─ assets/                 应用资源
├─ docs/                   架构、使用与审计记录
├─ skills/                 保留宿主调用约定
├─ data/                   持久用户数据；禁止缓存清理器删除
│  ├─ library/             经显式迁移的素材与学习资源
│  └─ transcriptions/      经辨别后保留的用户转写结果
├─ var/                    应用生成内容；按所属任务和保留策略维护
│  ├─ cache/
│  ├─ logs/
│  └─ test-artifacts/
├─ models/                 先保持实际路径；可选外置，不强制迁移
├─ runtimes/               先保持实际路径；不拆散现有环境
├─ .local/                 私有状态，进一步归类前保持兼容
├─ .venv/ .git/ .shuncode/  原位保留
└─ README、清单、薄兼容入口及双击启动器
```

不建议再增加万能 `utils/`、空的“领域/仓储”分层，或把模型、用户数据和源码全部塞入一个 `resources/`。目录少不是目标，**责任清楚、可备份、可恢复、不可误删**才是目标。

## 4. 兼容与恢复要求

1. 开始前记录当前 Git 状态、已存在改动、受影响文件哈希；不提交、重置或 stash 用户工作。
2. 目录移动前冻结相关任务并由用户确认维护窗口；现在运行的工作台不因提交方案而重启。
3. 先统一/验证路径解析，再改默认位置；旧目录仍存在时不能静默创建另一个空资料库，让用户误以为课程丢失。
4. 数据迁移清单必须包含源/目标、文件数/大小、资源 ID、哈希及回退步骤。保持项目 ID、逻辑资源标识、学习进度、字幕、AI、对话与个人笔记关联。
5. 不用默认目录联接或符号链接“糊住”迁移；现有资源安全检查明确拒绝链接/联接。确需兼容层时先设计并单独测试。
6. 不自动修改 `.env`、API 密钥、Cookie、个人笔记库或全局工具配置。由应用保存的绝对路径与原生 agent 绑定也需要逐项处理，不能只修前端。
7. 保留根部启动器及旧薄入口；在其他工作目录、中文/空格路径下验证 Web、CLI 与 Skill。
8. 每批验证离线回归、隔离构建和相应浏览器流程；数据迁移还必须验证恢复原位置、重新打开旧视频、字幕/聊天/笔记/进度可用，再进入下一批。
